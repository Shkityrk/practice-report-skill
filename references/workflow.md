# Порядок работы подробно

## Этап 0. Приём задания

Собрать: (1) файл методички, (2) пример оформления — прошлый отчёт(ы) пользователя (docx/pdf) и, если есть, документ
«Требования к выполнению практических работ», (3) данные для титульного листа, (4) ограничения среды (что нельзя трогать).
Папка работы обычно `…/pr-N/` рядом с прошлыми `pr-3`, `pr-4`…; методичка лежит внутри. Если в папке нет «Требований» —
сказать об этом и взять оформление с прошлых отчётов.

**Чтение PDF.** Внешних утилит (`pdftotext`, `pdftoppm`) на машине часто нет, поэтому есть `scripts/pdf_to_text.py`
(на pymupdf): печатает текст страниц и сохраняет PNG каждой страницы. Окружение — `scripts/setup_env.sh`.
Команды, YAML и код в методичках — частые КАРТИНКИ: если в тексте страницы после «выглядит следующим образом:» пусто
(или у страницы есть картинки), откройте её PNG инструментом Read. dpi 80 хватает для команд, для YAML берите 105+.

**Прошлые отчёты.** Извлеките из них: титульный лист (кто руководитель, кафедра), набор разделов, подписи рисунков,
как описываются скриншоты, длину ответов на вопросы. Генератор прошлых отчётов (`build_report.py`) — лучший образец;
`scripts/report_lib.py` уже содержит их оформление.

## Этап 1. План

`scripts/new_practice.py pr-N --no N --student-surname … --student-short "…" --group … --discipline … --supervisor …` создаёт каркас, затем заполнить `PLAN.md`
(шаблон `templates/PLAN.md`): таблица требований T1…, «что нужно от вас», окружение и риски, отступления, структура
папки, фазы, список скриншотов, чек-лист. План показывается пользователю ДО установок и запусков, вместе с вопросами.
Это же — точка, где озвучиваются варианты («по фамилии/группе»): что в методичке зависит от студента (имена ресурсов,
номер варианта) — спросить, а не угадывать.

## Этап 2. Окружение и безопасность

См. `references/safety.md`. Коротко: снять «хеш до» рабочих конфигов, изолировать окружение через `env.sh`, получить
явное «да» на установки/скачивания, не поднимать больше ресурсов, чем нужно.

## Этап 3. Реализация вручную

Прогнать всё один раз руками (Bash), не снимая скриншоты: цель — найти ошибки методички и убедиться, что система
работает. Каждое отступление записывать в таблицу «Отступления» в PLAN.md (оно пойдёт в отчёт отдельным подразделом).
Проверять не «Running», а поведение: запрос вернул ответ, данные пережили перезапуск, репликация работает.

## Этап 4. Съёмка

`report/shots.py` (шаблон `templates/shots.py`, библиотека `scripts/shots_lib.py`): чистое состояние → этапы по порядку
методички → кадры. Запуск в фоне с логом; пока идёт — писать текст отчёта. Затем ОТКРЫТЬ ключевые PNG и посмотреть
глазами (Read): обрезанные страницы, пустые выводы, секреты, «Terminating» в кадре. Нужные кадры переснять точечным
скриптом, не гоняя всё заново.

## Этап 5. Отчёт

`report/build_report.py` на `report_lib.Report`. Структура и шаблоны текста — `references/report-structure.md`.
Сначала собрать docx, потом сверить: сквозная нумерация рисунков, каждый рисунок упомянут в тексте, ответы на все
вопросы методички, раздел отступлений, выводы, источники.

## Этап 6. Завершение

Остановить кластеры/контейнеры/фоновые процессы, проверить «хеш после», показать пользователю итог: что сделано,
какие отступления, что осталось на его решение (удалить профиль, повторно запустить), вопросы по недостающему.
Пользователь отчёт сдаёт и защищает устно — в итоге дать 3–5 тезисов «что нужно уметь объяснить».
