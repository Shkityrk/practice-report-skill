# Общие грабли (применимы к любой практической работе)

Здесь только то, что повторяется от работы к работе. Специфику конкретной дисциплины сюда не добавлять: она живёт в
`PLAN.md` самой работы (раздел «Известные проблемы методички»).

## Методички и код из них

- Методичка — не истина в последней инстанции: версии API, образы, примеры кода и конфигурации в ней могут быть
  устаревшими или содержать ошибки. До съёмки скриншотов прогнать всё руками и убедиться в **поведении**
  (запрос вернул ожидаемое, данные пережили перезапуск, сервис доступен), а не в статусе «запущено».
- Исправлять минимально и записывать каждое отступление («что в методичке → что сделано → почему»): оно пойдёт в
  отчёт отдельным подразделом. Исходный код из репозиториев не править — адаптацию делать в отдельной папке.
- Примеры с небезопасными настройками (лишние права, пароли в открытом виде) не применять и объяснять почему.
- Команды, манифесты и код в PDF часто вставлены картинками: текстового слоя нет → открыть PNG страницы
  (`scripts/pdf_to_text.py`).
- Рекомендованные в методичке ресурсы (CPU/память/диск) могут не поместиться в среду — считать заранее.
- Если методичка предлагает интерактивное/долгоживущее действие (команда открывает браузер, держит терминал),
  запускать его в фоне с выводом в лог/URL и честно написать в отчёте, как сделано.

## Инструменты среды

- Нет `pdftotext`/`pdftoppm` → `scripts/pdf_to_text.py` (pymupdf). Нет `python-docx` в системном Python → venv
  (`scripts/setup_env.sh`), системный Python не трогать.
- Playwright хочет свой билд браузера → `find_chrome()` берёт уже скачанный; `playwright install` без «да» не запускать.
- Фоновые команды: `run_in_background`; прогресс-вывод утилит (загрузки, `> лог 2>&1`) не читать целиком — `tail`.
- Хуки Claude Code (если включены): «Fact-Forcing Gate» перед первым созданием/правкой файла просит назвать
  вызывающих, аналоги, схему данных и процитировать инструкцию пользователя — сказать это текстом и повторить вызов
  (повтор по тому же файлу проходит); `dcg` блокирует запись в путь через переменную (`cat > $VAR/x`) и
  «inline-интерпретатор в heredoc» → писать в буквальные пути и класть Python в отдельные .py-файлы;
  `sleep N` в Bash блокируется → ждать через `run_in_background` + `until`-цикл.
- Для длинной работы раскладывать файлы по папке работы сразу (скрипты съёмки/сборки рядом с `PLAN.md`), чтобы любую
  часть можно было пересобрать.

## Поведение с пользователем

- Спрашивать то, что знает только пользователь: ФИО, группа, руководитель, **варианты по фамилии/номеру**, недостающие
  документы. Не копировать чужие данные из старых файлов.
- Согласие на установку/скачивание — только явное; расплывчатое «делай аккуратно» согласием не считать.
- Пользователь может работать на ноутбуке: при жалобе на нагрев/тормоза проверить, что нагружает машину
  (`ps -Ao pcpu,comm -r`, при контейнерах — `docker stats`), снизить ресурсы, закончить быстро и всё остановить.
  Чужие процессы не трогать.
- В конце всегда: что сделано, какие отступления, что остановлено/осталось, 3–5 тезисов для устной защиты.

## Как пополнять этот файл

Добавлять только повторяющиеся и не зависящие от темы пункты (инструменты, процесс, общение). Тематические находки
оставлять в `PLAN.md` работы — иначе скилл перестанет быть универсальным.
