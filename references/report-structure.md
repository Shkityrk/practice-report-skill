# Структура отчёта и шаблоны текста

Образец — прошлые отчёты пользователя (по умолчанию оформление РТУ МИРЭА). Оформление уже зашито в `scripts/report_lib.py`
(TNR 14, 1.5, по ширине, отступ 1.25 см, поля 3/1.5/2/2, номера страниц снизу по центру, кроме титульного).

## Разделы (порядок)

1. **Титульный лист** — логотип (если задан), шапка вуза (`header` в config.json; по умолчанию РТУ МИРЭА), институт и кафедра (если заданы), «ПРАКТИЧЕСКАЯ РАБОТА №N»,
   дисциплина, студент/группа/подпись, руководитель/подпись, даты «Работа представлена / Допущен к работе», «Москва год».
2. **СОДЕРЖАНИЕ** — поле Word (обновляется при открытии).
3. **ЦЕЛЬ РАБОТЫ** — 1–3 предложения: «Изучить …, развернуть …, проверить …».
4. **ХОД РАБОТЫ** — вводный абзац (среда, где лежат файлы, как изолирована конфигурация), затем подразделы
   `1 …`, `2 …` по этапам методички, в конце — «Отличия от методического указания» (список).
5. **ОТВЕТЫ НА ВОПРОСЫ** — каждый вопрос методички подзаголовком, ответ 3–6 предложений.
6. **ВЫВОДЫ** — один абзац: что сделано → чем подтверждено → что важно.
7. **ИНФОРМАЦИОННЫЕ ИСТОЧНИКИ** — ссылки из методички + документация использованных инструментов.

Заголовки разделов — ПРОПИСНЫМИ, по центру, каждый с новой страницы; подзаголовки — жирные, по левому краю.

## Шаблон подраздела хода работы

> **N Название этапа** (соответствует заголовку/абзацу методички)
> Абзац 1: *что делаем и зачем* + точная команда в тексте (`команда`).
> `figure(...)` — скриншот.
> Абзац 2: *что видно на рисунке*: расшифровка 2–4 ключевых полей вывода (что означают ключевые колонки и поля вывода).
> Если этап имеет «подвох» — одно предложение почему так (ограничение драйвера, версия API).

Правило: рисунок не висит без текста. Каждый рисунок упомянут/объяснён рядом, подпись `Рисунок N – …` краткая и
предметная («Результат проверки доступности сервиса», а не «Скриншот 4»).

## Ответы на вопросы

Формула: определение (1 предложение) → зачем/как работает (2–3) → пример из этой работы (1). Пример:
«Контейнер – изолированный процесс со своим окружением и файловой системой, запускаемый из образа. … В работе приложение запущено в контейнере из собранного образа.»
Ответы должны быть такими, чтобы студент мог их пересказать на защите.

## Отступления от методички

Отдельный подраздел списком: «что в методичке → что сделано → почему». Типовые причины: устаревшая версия API,
ошибка в примере, ограничение драйвера/ОС, нехватка ресурсов, небезопасная настройка. Это защита студента: проверяющий
видит осознанность, а не расхождение.

## Таблицы и листинги

Таблица — только если есть что сопоставлять (требование ↔ реализация, список сервисов). Подпись «Таблица N – …»
над таблицей. Листинг кода/YAML в тексте — редко: обычно манифесты показываются скриншотом `cat файл`.

## Имена файлов и несколько студентов

`<Фамилия>_ПР<N>_отчет.docx` в `report/`. По умолчанию — один студент (владелец сессии). Отчёты для других людей
делать только по явной просьбе и с их данными; тогда `build_report.py "Фамилия" "Ф.И.О."` меняет только титульный
лист (если пользователь просит различий — меняйте имена артефактов и тестовые данные, но не выдумывайте результаты).
